## 2026-10-22 · The service worker: only its own caches, and deploys it survives

- **Why, 1: the origin is shared.** vdm285.github.io serves the owner's Pages apps (Papelito at `/papelito/`, A cómo at `/a-como/`, Tabla Viva at `/interactive-science/`, this one at `/giramundo/`), and Cache Storage belongs to the origin, not the path. The activate step of the committed `public/sw.js` (HEAD) deletes every cache not named `giramundo-v2`, the other apps' offline copies included. This one deletes only this app's retired caches, by exact name: `globo-curioso-v1` and `giramundo-v1` (from git history). No prefix: a cache named `giramundo-anything` that is not one of these stays.
- **Why, 2: HEAD keeps all of its own.** HEAD's worker (1,597 bytes) has no build stamp and no prune. Its `sw.js` is the same file in every build, so a deploy installs no new worker; files under `assets/` are cache first and never deleted, so the cache keeps every deploy's code (one code deploy added B's 3 new files, 0.76 MB, and removed nothing: "Before" below), and each link with a query string (`?fbclid=`) keeps one more copy of the page.
- **Why, 3: Pages' HTTP caching, and why the page is now revalidated.** Pages answers every file with `Cache-Control: max-age=600` and an ETag that changes on every deploy (live headers checked today: `ETag: "<deploy time>-<size>"`, `Age`, `Vary: Accept-Encoding`; a 404 has no max-age): across a deploy a revalidation is a full download, within one deploy a 304. HEAD fetches with the default cache mode, so within ten minutes of a visit a reopen after a deploy serves and stores the old page from the HTTP cache. That is consistent with its code, which HEAD still holds: the old build renders, online and offline, until the HTTP cache expires. A worker that prunes old code cannot do that, since the old page would name code it has deleted; nor may it keep a page whose code it never got. Hence a revalidated page, an install that caches a build's code before its page, and a stamped worker that keeps only its own build's page.
- **Who runs this worker.** The app has not registered it since bc0876c (2026-10-16 17:33Z): the `register` call left with the old `src/ui/app.js`, and "Shipped" below still lists the worker. Only browsers that opened `/giramundo/` between the deploys of ef94623 (16:43Z, the rename that moved the base to `/giramundo/`) and bc0876c registered it; each later visit of theirs updates it to the `sw.js` then live (today HEAD's, 1,597 bytes). The registrations from 2026-10-15 live at `/interactive-globe/`, whose `sw.js` now answers 404: their updates fail and they touch nothing. Registering the worker again is the owner's call (sizes below).
- **The rules** (the comments at the top of `public/sw.js` say the same). The page: network first, always revalidated, kept under one key, `./`; when the network fails, stalls for 3.5 s or answers 404/5xx, the kept page answers if there is one. Files under `assets/` (code, styles, fonts): cache first; their names are hashed, so a new build brings new names; install caches this build's and activate prunes the others. The data JSON (anything not named here): network first and revalidated, the cached copy offline. **Textures, flags and images (`.png`, `.jpg`, `.svg`) outside `assets/`: cache first forever, never revalidated. A changed one needs a new file name**, or every browser with the worker keeps the old one.
- **What changed.** `public/sw.js`: navigations fetch the page with `cache: 'no-cache'` (a 304 when unchanged), raced against 3.5 s: a stall, a network error or a 404/5xx gets the kept `./` (with nothing kept, a stall waits on and an error is passed through; a navigation to anything but `./` and `index.html` first tries its own cached copy, as before). The page is kept under one key, `./`, whatever the link added (`?fbclid=`, `index.html`); activate deletes the per-link copies earlier workers kept. A stamped worker keeps a page under `./` only when every `assets/` file it names is in its own list: a newer build's page, fetched while the old worker still runs, is shown but not stored, and that build's own install stores it (code first, page last); unstamped, every page that comes back ok is kept. Install fetches `./` the same way and this build's listed files under `assets/` except the `.woff` fallbacks, skipping what is already cached, and stores the page last, so the cache holds one consistent build before activate prunes the last one; a page that names a file outside this build's list (a CDN copy not yet updated) fails the install, and the current worker stays. Activate prunes the `<scope>assets/` files the list does not name, only when the list is non-empty (unstamped, as the dev server serves it: no precache, no prune). The other network-first requests (the data JSON) are fetched with `cache: 'no-cache'` too. The offline fallback now awaits `cache.match('./')` (HEAD returns the promise, so `|| Response.error()` never applies). `vite.config.js`: `swStamp` (build only, on the configured outDir) writes the build's `assets/` list and an id into the built `sw.js`, and fails the build when `assets/` is empty, when the entry script of the built `index.html` (or any `assets/` file it names) is not in the list, or when the placeholders are missing. The same code stamps the same id (`a8594a50711d` in the three builds of today's code with the real base), so a data-only redeploy (the six-hourly news run) leaves `sw.js` byte-identical and nothing reinstalls.
- **How it was measured.** `data/cache/sw-pages/run.mjs` and `suite.sh` (gitignored): real Chrome 155 (headless, puppeteer-core) against a server on 127.0.0.1:5212 that answers like Pages (max-age=600, ETag from deploy time and size, 304 on If-None-Match, Age 0, Vary; a deploy changes every ETag). Builds A and B made with `VITE_BASE=/giramundo/`; B adds one line to `app.js` at transform time, so `index`, `app` and `scene` re-hash (761,362 bytes; the working tree is not touched). Steps: first visit to A and register the worker; visit again; a `?fbclid=` link; deploy B; reopen (a new tab); the new worker activates; reopen; stop the server; offline start; offline start once the HTTP cache has expired. "Renders" means `#ui` holds the shell, `window.giramundo` is set and `#boot-error` stays hidden. Variants: deploy within 10 minutes of the first visit; a returning reader (the last visit refreshed only the page in the HTTP cache, the code came from the worker's cache); the reopen after the HTTP cache expired (the control); `sw.js` of B while the page is still A's. "The HTTP cache expired" is `Network.clearBrowserCache` (Cache Storage untouched, checked each time); three runs replaced the first of these with a real 610-second wait and gave the same results as their stand-in runs. A reviewer's harness, `data/cache/sw-skeptic/run.mjs`, adds scenarios on the same kind of server: `headOnly` (HEAD's worker across a code deploy, within ten minutes, then after the HTTP cache expired), `cutoff` (the first load after a deploy gets the new page and never its new code, then offline), `liefi` (the page request is accepted and never answered) and `pageError` (the page answers 503, 500, then 404, then a navigation to a page that does not exist). `data/cache/sw-fix/unit.mjs` runs the navigation branches against mocks.
